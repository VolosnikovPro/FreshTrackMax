Проект: FreshTrackMax

## Рекомендуемые настройки запуска

- Модель: `gpt-5.6-terra`.
- Уровень рассуждений: `medium`.
- Режим работы: реализация в текущем проекте с тестами, без подключения к production и без деплоя.

`gpt-5.6-terra / medium` достаточно для этой задачи: здесь нужна аккуратная сквозная правка frontend, API, БД и тестов, но архитектура и критерии уже описаны. Не трать токены на повторное проектирование. Сначала проверь фактический код, затем реализуй задание до конца. Не останавливайся на плане.

## Цель

Исправить работу FreshTrackMax с несколькими объектами и реализовать безопасный импорт нового расхода сырья из файла.

После изменений выбранный пользователем объект должен быть единым контекстом для дашборда, списков, операций создания/изменения и импортов. Файл расхода содержит только новые операции за период, поэтому каждая успешная загрузка добавляет расход и списывает остатки по FEFO. Повторная загрузка того же файла не должна повторно списывать сырье.

## Подтвержденные причины ошибок

Перед изменениями проверь эти выводы по актуальному коду, но не начинай новое широкое исследование:

1. Frontend хранит `currentSiteId`, но часть страниц не перезагружается при его изменении: в `useEffect` отсутствует зависимость от выбранного объекта.
2. Часть запросов создания, изменения и импорта не передает `site_id`.
3. Backend использует разные правила определения объекта. Списки частично принимают выбранный объект, а дашборд и импорт используют объект из профиля пользователя.
4. Поэтому файл может попасть в один объект, список показывать другой, а счетчик дашборда считать третий контекст.
5. Импорт себестоимости сейчас не создает операции расхода и не выполняет FEFO-списание.
6. В затрагиваемых маршрутах `costs` и `headcount` возможно двойное присваивание `site_id`, приводящее к `TypeError/500`.

В первую очередь изучи:

- `frontend/src/hooks/useSite.tsx`
- `frontend/src/components/common/Layout.tsx`
- `frontend/src/api/index.ts`
- страницы Dashboard, Products, Batches, Costs, Consumption, Headcount и Admin
- `backend/app/api/routes/admin.py`
- `backend/app/api/routes/sites.py`
- маршруты products, batches, costs, consumption, headcount и sheets
- `backend/app/services/import_service.py`
- `backend/app/services/consumption_service.py`
- модели SQLAlchemy, настройку БД и существующие тесты импорта/расхода
- реальные примеры XLSX в репозитории

Сначала выполни `git status`. Рабочее дерево может содержать изменения пользователя: не откатывай, не форматируй и не перезаписывай их без необходимости.

## 1. Единый контекст объекта

Создай один backend-механизм определения эффективного объекта и используй его во всех затрагиваемых маршрутах вместо дублирующихся локальных `_get_site_id`.

Правила доступа:

- `admin` и `manager` могут выбрать любой активный объект;
- остальные роли работают только со своим объектом, даже если подставят чужой `site_id` вручную;
- неизвестный или неактивный объект должен давать согласованную ошибку;
- попытка доступа к чужому объекту должна давать `403`, а не утечку данных;
- список доступных объектов должен соответствовать этим правилам: `admin` и `manager` видят активные объекты, остальные только свой.

Применить эффективный `site_id` к:

- dashboard summary;
- спискам и карточкам сырья, партий, себестоимости, расхода и численности;
- create/update/delete для этих сущностей;
- файловому импорту и импорту Google Sheets, если этот путь уже поддерживается;
- любым связанным запросам, которые выполняются после переключения объекта.

Frontend должен явно передавать текущий `site_id` во все соответствующие API-вызовы. Все страницы, зависящие от объекта, обязаны повторно загружать данные при изменении `currentSiteId`. При переключении не должно оставаться данных, формы или счетчиков предыдущего объекта.

Исправь найденную передачу `site_id` дважды в create-маршрутах costs/headcount и добавь регрессионную проверку.

## 2. Импорт риск-отчета и себестоимости

В разделе импорта объект должен быть видимым и обязательным полем. По умолчанию используй текущий объект из глобального переключателя. Пользователь должен однозначно видеть, куда загрузится файл.

Требования:

- передавать `site_id` для файла и Google Sheets;
- backend повторно проверяет права на объект;
- риск-отчет и файл себестоимости изменяют данные только выбранного объекта;
- успешный ответ сообщает название/ID объекта и число созданных/обновленных строк;
- после успеха связанные страницы и дашборд показывают данные выбранного объекта без ручного выхода из аккаунта;
- существующую семантику риск-отчета не менять без необходимости: это отдельный импорт остатков, а не расход.

## 3. Новый импорт расхода сырья

Добавь отдельный тип импорта, например `consumption_file`. Не маскируй его под импорт себестоимости.

### Семантика

- каждый файл содержит только новый, ранее не проведенный расход;
- успешная загрузка создает новые операции расхода;
- остатки партий уменьшаются по FEFO через существующий `consumption_service` или его аккуратно расширенную версию;
- данные прошлых импортов не заменяются и не пересчитываются;
- точный повтор одного файла блокируется до списания.

### Поддерживаемый формат

Сначала изучи примеры XLSX в репозитории и существующий парсер. Поддержи фактический клиентский формат, не угадывая номера строк только по одному тесту.

Минимальный канонический формат строк:

`Дата | Код/Артикул | Товар | Ед. изм. | Количество`

Допустимы согласованные русские варианты названий колонок. Код может отсутствовать, если товар можно однозначно найти по нормализованному названию.

Если клиентский файл является матрицей с колонками-днями (`1`, `2`, `3`...), в UI сделай обязательным выбор месяца и года. Каждая положительная ячейка под днем `N` превращается в новую операцию на дату `год-месяц-N`. Невозможные даты считаются ошибкой валидации. Пустые и нулевые ячейки пропускаются. В итоговом отчете укажи, какой распознан формат.

### Поиск сырья

Ищи товар только внутри выбранного объекта:

1. по коду/артикулу, если он указан;
2. иначе по нормализованному точному названию.

Не создавай новое сырье молча во время импорта расхода. Неизвестное или неоднозначное сырье является ошибкой всего файла с указанием строки/ячейки.

### Атомарность и FEFO

Обработка файла должна быть одной атомарной бизнес-операцией:

1. прочитать и нормализовать все строки;
2. проверить объект, формат, даты, товары и положительность количества;
3. агрегировать потребность по товару и проверить достаточность остатка для всего файла;
4. защититься от конкурентного списания блокировкой строк партий или эквивалентным механизмом транзакции;
5. только после полной проверки создать операции расхода и уменьшить партии по FEFO;
6. при любой ошибке откатить все изменения файла.

Частичный импорт запрещен. Нельзя создать часть расхода и вернуть ошибку по оставшимся строкам.

## 4. Защита от повторного файла

Добавь сущность истории импортов, например `ImportRun`, и миграцию для существующей production-БД.

Минимальные поля:

- `id`;
- `site_id`;
- `import_type`;
- исходное имя файла или источник;
- `sha256` содержимого файла;
- `status`;
- `created_by`;
- `created_at`;
- количество прочитанных и проведенных строк;
- краткая ошибка или структурированный результат, если это согласуется с текущей моделью проекта.

Добавь уникальное ограничение как минимум на `(site_id, import_type, sha256)`. Проверка в коде нужна для понятного ответа, а ограничение БД является защитой от гонки.

Повтор успешного файла возвращает `409 Conflict` и понятное русское сообщение с датой предыдущего импорта. Никаких новых операций и изменений партий быть не должно.

Неудачный запуск того же файла разрешено повторить после исправления причины. При этом уникальная запись истории должна безопасно переиспользоваться или переводиться из `failed` в `processing` под блокировкой; два параллельных запуска одного файла не могут одновременно перейти к списанию. Статусы `processing`, `success` и `failed` должны отражать реальное состояние, а падение процесса не должно оставлять вечный ложный `processing` без предусмотренного восстановления.

Не рассчитывай только на `create_all`: база уже существует. Добавь воспроизводимую миграцию и инструкцию ее применения. Если Alembic в проекте отсутствует, внедри минимальный стандартный Alembic без автоматического запуска миграций при старте приложения.

## 5. Ошибки API и интерфейс

Для импорта возвращай структурированный результат:

- `site_id` и имя объекта;
- тип и распознанный формат;
- число строк/операций;
- число затронутых товаров и партий;
- суммарное списанное количество, если единицы сопоставимы;
- список ошибок с номером строки, колонкой/днем и причиной.

Ошибки валидации файла должны отображаться пользователю без технического traceback. Для недостаточного остатка показать товар, требуемое и доступное количество. Для повторного файла показать, что он уже загружен. Существующий интерфейс и дизайн-систему сохранить, новые декоративные страницы не создавать.

## 6. Тесты

Пиши тесты до или вместе с изменением поведения. Обязательные сценарии:

1. `admin` и `manager` читают и изменяют выбранный разрешенный объект.
2. Остальные роли не могут получить или изменить чужой объект подстановкой `site_id`.
3. Переключение объекта меняет dashboard и все затронутые списки без смешивания данных.
4. Риск-отчет и себестоимость импортируются именно в переданный объект.
5. Успешный импорт расхода создает операции и списывает несколько партий в FEFO-порядке.
6. Повтор того же файла возвращает `409` и не меняет расход/остатки.
7. Одинаковое имя с другим содержимым не считается дубликатом.
8. Неизвестный товар, неверная дата, отрицательное количество и неоднозначное совпадение откатывают весь файл.
9. Недостаточный остаток для одной строки откатывает весь файл.
10. Двойное конкурентное списание не может увести остаток ниже нуля.
11. Создание costs/headcount больше не падает из-за двойного `site_id`.
12. Миграция применяется к непустой существующей БД и откатывается штатно.

Добавь небольшие XLSX-фикстуры для канонического и фактического матричного формата. Не включай клиентские персональные данные в тесты.

## 7. Границы задачи

Не выполнять SSH-подключение, деплой и изменения production-БД. Не включать в код, тесты, документацию или коммиты пароли, токены, `.env`, сертификаты и реальные персональные данные.

Не исправлять попутно остальные замечания аудита, если они не блокируют описанный поток. Не проводить массовый рефакторинг. Соблюдать существующую архитектуру, стили API и UI.

## Критерии приемки

Задача считается выполненной, когда:

- выбранный объект единообразно применяется во всех перечисленных чтениях и записях;
- переключение объекта не вызывает ошибку и сразу обновляет данные;
- пользователь явно выбирает объект для риск-отчета, себестоимости и расхода;
- загруженное сырье видно в списке и дашборде одного и того же объекта;
- новый файл расхода атомарно списывает партии по FEFO;
- точный повтор файла надежно блокируется по SHA-256;
- неудачный импорт не оставляет частичных изменений;
- все новые и существующие релевантные тесты проходят;
- миграция и действия перед деплоем описаны, но production не изменен.
